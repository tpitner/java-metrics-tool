= Validation corpus
:toc: left
:toclevels: 2

This directory contains a small, manually reviewable corpus for validating
`java-metrics` and external measurement providers against the same sources. It
is not an empirical dataset for the research article. Its purpose is to
distinguish adapter defects, differences in operational definitions, and
defects in the measured tool.

== Oracle model

An oracle is an independently established expectation against which an actual
result is checked. The corpus has three layers:

* the _build oracle_ records whether a case is expected to compile;
* the _subject oracle_ identifies the logical types that a provider must find
  and map unambiguously;
* the _measurement oracle_ records the expected status and value of a metric
  according to its explicit operational definition.

An external metric tool is not an oracle by itself. CK and other tools are
useful differential-testing targets, but a disagreement may identify an
adapter defect, an external-tool defect, or a legitimate definition mismatch.
The `provider` column binds each expectation to a particular definition and
prevents similarly named metrics from being conflated.

== Structure

`cases.csv`::
The case manifest. It defines the stable `case_id`, Maven project directory,
source root, expected build outcome, and construct under test.

`subjects.csv`::
The oracle of addressable logical types. A provider-specific mapper must link
each required entry to the same logical subject. Local and anonymous types are
present in the sources but are not required here until their cross-tool
identity has been frozen.

`measurements.csv`::
The manually reviewed measurement oracle. Each row identifies a case,
provider, metric, scope, subject, status, value relation, and optional value or
bounds.

`ck-exclusions.csv`::
Explicit CK-specific exceptions to the subject oracle. Every exception has a
reason, and tests check whether the exception has become obsolete. The pinned
CK revision, for example, emits no `class.csv` row for an annotation
declaration.

`cases/<case-id>/`::
Small independent Maven projects without external dependencies. Each case can
be compiled separately and passed to CK.

== Cases

[cols="1,1,3",options="header"]
|===
|Case |Expected build |Purpose

|`basic-members` |success
|Empty type and explicit fields, constructors, and methods.

|`inheritance` |success
|Multilevel inheritance and multiple direct children.

|`interfaces` |success
|Interface inheritance, a default method, and an implementing class.

|`coupling` |success
|Dependencies across three packages through fields, constructors, return
types, and calls.

|`overloads` |success
|Overloaded methods and constructors with equal and different arities.

|`nested-types` |success
|Static nested, inner, local, and anonymous classes.

|`modern-types` |success
|A record, enum, annotation, and sealed hierarchy in Java 17.

|`initializers-lambdas` |success
|Static and instance initializers and lambda-expression subjects.

|`unresolved-dependency` |failure
|Syntactically valid source with a missing external type. A source provider may
analyse it, while a bytecode provider must report unavailability rather than
silently exclude it.
|===

== Running the corpus

The default tests validate the manifest, expected build status, subject
mapping, and built-in measurement oracle:

[source,bash]
----
mvn test
----

`CkValidationCorpusTest` is opt-in because it executes a separately obtained CK
JAR. It runs CK over every case, validates the required type mappings and
provider-specific exclusions, and compares all `provider=ck` oracle rows:

[source,bash]
----
mvn test -Dtest=CkValidationCorpusTest \
  -Dck.jar=/absolute/path/to/ck.jar \
  -Dck.java=/absolute/path/to/jdk-21/bin/java
----

Maven and `java-metrics` run on Java 21. The `ck.java` property is required
together with `ck.jar` and explicitly selects the Java 21 executable used for
the external CK process.

== CK validation boundary

The pinned CK revision has explicitly controlled mapping limits: local and
anonymous types do not yet have a frozen cross-tool identity, an annotation
declaration has no `class.csv` row, and CK emits two method-like initializer
rows even though initializer scope is outside the published CK adapter
contract. Any other mapping diagnostic fails the test.

The manually reviewed CK oracle covers:

* type-level method/public-method and field/public-field counts, DIT, and NOC;
* method- and constructor-level parameter counts;
* WMC, RFC, and LOC for all 61 stable type, method, and constructor subjects;
* type- and member-level coupling metrics;
* type-level LCOM, LCOM*, TCC, and LCC.

Member subjects use the canonical form `owner#method(types)` or
`owner#<init>(types)`. Signatures distinguish overloads. If a parameter type
binding is unresolved, the syntactically available name is retained instead of
inventing a fully qualified name.

CK RFC is the number of unique method and super-method invocation nodes, not a
traditional response-set calculation. CK LOC represents lines in CK's
normalized AST rendering, not physical source lines.

== Built-in validation boundary

The built-in oracle covers declared member counts, physical LOC and NCLOC,
LCOM4, and package-level `Ca`, `Ce`, instability, abstractness, and distance.
Package subjects use fully qualified package names. Interval expectations use
the `lower` and `upper` columns.

The overall validation strategy and current release boundary are summarized in
`../docs/validation.adoc`.

== Extension rules

* Add one new construct as the smallest independent case or as a clearly
  justified extension to an existing case.
* Derive oracle values manually or by an independent procedure; output from
  the provider under test cannot be its own oracle.
* Do not compare equally named metrics from different providers without first
  checking their operational definitions.
* Keep a non-compiling case in the manifest and in any future selection funnel;
  do not remove it merely to accommodate a bytecode provider.
