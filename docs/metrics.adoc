= Metrics
:toc: left
:toclevels: 2

Every published metric has a provider-qualified `MetricId`, supported scope,
unit, and specification key. Metrics implemented by `java-metrics` use the
`java` namespace. Metrics imported from CK use the `ck` namespace so that
similarly named metrics with different operational definitions are not
silently conflated.

== Built-in Java provider

|`java.physical-loc`, `java.ncloc`

|`java.physical-loc-exclusive`, `java.ncloc-exclusive`

|Type lines excluding nested type ranges.

|`java.lcom4`
|type
|LCOM4 connected components over eligible instance methods, shared instance
fields, and direct intra-type calls.

|`java.ca`, `java.ce`

|Afferent and efferent coupling over internal package dependencies.

|`java.instability`, `java.abstractness`, `java.distance`
|package

|===

Cyclomatic complexity, WMC, DIT, NOC, CBO, fan-in, fan-out, and RFC have
catalog identifiers but no built-in metric computer. They must not be
advertised under the `java` namespace. The corresponding supported CK metrics
are available only when the optional CK provider is enabled.

=== Operational definitions

The specification keys below are stable identifiers stored in the metric
catalog. They distinguish these definitions from similarly named metrics in
other tools.

==== Declared members

`java.declared-methods` (`t2.declared-methods.v1`),
`java.declared-constructors` (`t2.declared-constructors.v1`), and
`java.declared-fields` (`t2.declared-fields.v1`) count the corresponding AST
members declared directly by a type. Inherited members and members of nested,
local, or anonymous types are not added to the enclosing type. Each nested
type is measured separately. Multiple variables declared by one field
declaration are represented and counted as separate fields.

==== Source lines

`java.physical-loc` (`t2.physical-loc.v1`) counts physical lines intersecting
the subject's source range. At file scope it is the number of lines in the
file, including blank and comment-only lines; an empty file has zero lines.
Project and package values are sums of their distinct input files. Type,
method, constructor, initializer, and lambda values are inclusive source-range
counts, so lines belonging to nested subjects can also belong to their parent.

`java.ncloc` (`t2.ncloc.v1`) counts lines containing at least one
non-whitespace source token after JDT comment ranges have been removed. Blank
and comment-only lines do not count. A text block is treated as one source
token: its delimiter lines count when they contain the token, while its
interior text is not mistaken for Java code.

`java.physical-loc-exclusive` (`t2.physical-loc-exclusive.v1`) and
`java.ncloc-exclusive` (`t2.ncloc-exclusive.v1`) apply only to types. They use
the same rules but remove the source ranges of directly nested types. Because
every nested type is itself measured, this prevents double counting when type
measurements are aggregated. Local and anonymous type ranges are included in
this exclusion when represented as children of the measured type.

==== LCOM4

`java.lcom4` (`t2.lcom4.v1`) is the number of connected components in an
undirected graph of eligible methods declared by one type. Constructors,
static methods, abstract or otherwise body-less methods, and trivial field
accessors are not vertices. Two vertices are joined when they directly call
one another or access a common declared instance field. A call through a
trivial accessor contributes the fields accessed by that accessor.

Interfaces and annotations, types with no eligible methods, static utility
types, and accessor-only types receive `NOT_APPLICABLE` with a reason code.
One eligible method yields the exact value 1 and is marked as low-information
evidence. Unresolved field references or intra-type calls can only hide graph
edges and merge components; the observed component count is therefore emitted
as a `PARTIAL` upper bound rather than as an exact value.

==== Package coupling and derived ratios

The coupling universe is the set of packages present in the analysed input.
An internal directed package dependency exists when source in package `P`
refers to a resolved type declared in a different analysed package `Q`.
Multiple type-level references between the same ordered pair of packages count
once. Self-dependencies, JDK packages, and resolved external packages do not
enter the internal coupling counts.

For a package `P`:

* `java.ca` (`t2.ca.v1`) is the number of distinct analysed packages with an
  internal edge to `P`;
* `java.ce` (`t2.ce.v1`) is the number of distinct analysed packages to which
  `P` has an internal edge;
* `java.instability` (`t2.instability.v1`) is `Ce / (Ca + Ce)`.

If `Ca + Ce = 0`, instability is `NOT_APPLICABLE` when dependency resolution
is complete. With unresolved package targets it is instead the interval
`[0, 1]`. Unresolved targets make `Ca` and `Ce` lower bounds and make a derived
instability value partial; diagnostic attributes report internal, external,
JDK, and unresolved dependency counts separately.

`java.abstractness` (`t2.abstractness.v1`) is `Na / Nc`, where `Nc` is the
number of eligible top-level classes, interfaces, records, and enums in the
package, and `Na` is the number of those types that are interfaces or abstract
classes. Nested types and annotation declarations are excluded. A package with
no eligible top-level types receives `NOT_APPLICABLE`.

`java.distance` (`t2.distance.v1`) is the normalized distance from the main
sequence, `|abstractness + instability - 1|`. It is `NOT_APPLICABLE` if either
operand is not applicable. An interval or partial instability is propagated
to a conservative distance interval or partial value rather than collapsed to
an exact number.

=== Measurement status

`OK` means an exact value under the applicable definition. `PARTIAL` carries a
value relation (for example lower bound, upper bound, observed fragment, or
interval), reason codes, and available coverage evidence. `NOT_APPLICABLE`
means the definition intentionally has no value for the subject.
`UNAVAILABLE` means a value should be meaningful but the required evidence
could not be obtained. Consumers must not replace any non-`OK` status with
zero.

== Optional CK provider

The CK adapter is frozen to upstream revision `8a1ef91` and imports:

* CBO, modified CBO, fan-in, fan-out, WMC, RFC, and LOC at the type, method,
  and constructor scopes for which CK supplies values;
* DIT, NOC, LCOM, LCOM*, TCC, LCC, total/public method counts, and total/public
  field counts at type scope;
* parameter count at method and constructor scope.

CK definitions retain CK semantics. For example, CK RFC is derived from unique
method and super-method invocation nodes, and CK LOC reflects CK's normalized
AST rendering rather than physical source lines.

== Completeness and aggregation

A measurement is `OK`, `PARTIAL`, `NOT_APPLICABLE`, or `UNAVAILABLE`. Missing
bindings and unresolved dependencies are represented explicitly; they are not
silently replaced with zero.

Primary project aggregation uses only exact `OK` values. Partial measurements
are handled separately as lower bounds, upper bounds, or intervals with
coverage evidence. The programmatic `ProjectAggregationExporter` serializes
aggregation results as deterministic JSON or CSV. Aggregation is not a CLI
output mode in version 1.1.0.

The release scope and exclusions are normative in
`jors-release-scope.adoc`.
