CLI analyzátor Java zdrojových souborů založený na Eclipse JDT Core 3.47.0.

== Spuštění

Jeden soubor:

[source,bash]
----
mvn -q package
java -jar target/java-metrics-1.0-SNAPSHOT.jar cesta/k/Soubor.java
----

Adresář nebo celý balík/modul (rekurzivně):

[source,bash]
----
java -jar target/java-metrics-1.0-SNAPSHOT.jar cesta/k/adresari
----

Dodatečné zdrojové cesty (jako `--sourcepath` v `javac`) — všechny nalezené
`.java` soubory se naparsují a balíky se sloučí podle názvu balíku:

[source,bash]
----
java -jar target/java-metrics-1.0-SNAPSHOT.jar cesta/k/Soubor.java \
     --sourcepath cesta/k/dalsi-zdroje:cesta/k/dalsi
----

Vypnutí rekurze pro adresářový vstup:

[source,bash]
----
java -jar target/java-metrics-1.0-SNAPSHOT.jar cesta/k/adresari --no-recursive
----

Maven projekt:

[source,bash]
----
java -jar target/java-metrics-1.0-SNAPSHOT.jar --pom pom.xml
----

=== TOML konfigurace

Celý běh lze popsat explicitním konfiguračním souborem. Nástroj konfiguraci
automaticky nevyhledává; soubor se vždy předává přes `--config`. Výchozí
ukázka je v `java-metrics.example.toml`:

[source,bash]
----
mvn -q package
java -jar target/java-metrics-1.0-SNAPSHOT.jar \
  --config java-metrics.example.toml

# Pouze kontrola typů, klíčů, cest a vzájemných omezení:
java -jar target/java-metrics-1.0-SNAPSHOT.jar \
  --config java-metrics.example.toml --validate-config

# Deterministická výsledná konfigurace po aplikaci defaults a CLI overrides:
java -jar target/java-metrics-1.0-SNAPSHOT.jar \
  --config java-metrics.example.toml --format json --print-effective-config
----

Konfigurace používá TOML schema verze 1 a parser TomlJ. Neznámý klíč,
nesprávný typ, nepodporovaná metrika nebo neplatná kombinace jsou chyby;
nepodporujeme `include`, interpolaci environment variables ani spouštění
shellových výrazů. Relativní cesty v TOML se vyhodnocují vůči adresáři
konfiguračního souboru. Relativní cesty z CLI se vyhodnocují vůči aktuálnímu
pracovnímu adresáři.

Precedence je `vestavěné defaults < TOML < explicitní CLI`. CLI tedy může
například jednorázově změnit formát, aniž by měnilo soubor. Úplný příklad:

[source,toml]
----
schema-version = 1

[project]
inputs = ["src/main/java"]
recursive = true
include-tests = false
compile = true
sourcepath = []
classpath = []
release = "27"

[output]
format = "json"
destination = "target/metrics/result.json"
retain-provider-artifacts = false
provider-artifacts-directory = "target/java-metrics/providers"

[providers.java]
enabled = true
metrics = [
  "java.declared-methods",
  "java.declared-constructors",
  "java.declared-fields",
  "java.physical-loc",
  "java.ncloc",
  "java.physical-loc-exclusive",
  "java.ncloc-exclusive",
  "java.lcom4",
  "java.ca",
  "java.ce",
  "java.instability",
  "java.abstractness",
  "java.distance",
]

[providers.ck]
enabled = false
# Cesta je pouze příklad; v přenositelném běhu ukažte na připnutý CK JAR:
# jar = "../ck/target/ck-0.7.1-SNAPSHOT-jar-with-dependencies.jar"
java-executable = "/path/to/jdk-21/bin/java"
use-jars = true
max-files-per-partition = 0
variables-and-fields = true
ignored-directories = [".git", "target", "build"]
timeout-seconds = 600
retain-raw-csv = true
----

`providers.java.metrics` vybírá pouze skutečně počítané built-in metriky.
`providers.ck.enabled = true` aktivuje `CkMetricsProvider`; `jar` je potom
povinný a musí ukazovat na čitelný standalone JAR. CK se spouští jako oddělený
proces a jeho JDT se nelinkuje do procesu `java-metrics`.
`variables-and-fields = true` je při zapnutém CK povinné, protože bez
`MethodLevelFieldUsageCount` publikuje CK neplatné nulové TCC/LCC; konfigurace
`false` je validátorem odmítnuta.

Pro reprodukovatelnost se do JSON baseline ukládá cesta a SHA-256 zdrojového
TOML (je-li použit), deterministický effective TOML, jeho SHA-256 a seznam
hodnot přepsaných přes CLI. Effective konfigurace obsahuje normalizované
absolutní cesty.

=== CK provider

Pro lokální připnutý checkout lze sestavit a zapnout CK takto:

[source,bash]
----
(cd ../ck && mvn -DskipTests package)

# V java-metrics.example.toml nastavte:
# [providers.ck]
# enabled = true
# jar = "../ck/target/ck-0.7.1-SNAPSHOT-jar-with-dependencies.jar"

mvn -q package
java -jar target/java-metrics-1.0-SNAPSHOT.jar \
  --config java-metrics.example.toml --format json
----

`CkProcessRunner` vytváří pro každý běh nový output adresář, předává upstream
CLI argumenty bez shellu, zachycuje stdout/stderr, vynucuje timeout a kontroluje
exit kód i vznik `class.csv`/`method.csv`. Raw soubory se zachovají pouze pokud
jsou současně zapnuté `output.retain-provider-artifacts` a
`providers.ck.retain-raw-csv`; jinak se dočasný adresář po importu odstraní.

CSV kontrakt je zmrazen pro revizi `8a1ef91` a popsán v
`docs/20-ck-csv-schema.adoc`. Jakákoli změna pořadí nebo názvu sloupce je fatální
chyba. Importovaná první sada zahrnuje class- a method-level varianty CBO,
modified CBO, fan-in/out, WMC, RFC a LOC; dále type-level DIT, NOC, LCOM,
LCOM*, TCC, LCC a počty metod/polí a method/constructor-level počet parametrů.
Hodnota CK `NaN` se ukládá jako `NOT_APPLICABLE`, nikoli jako nula.

JSON obsahuje obecná pole `providerRuns` a `measurements`. CK provenance nese
verzi, SHA-256 JARu, úplný příkaz, Java runtime, efektivní CK volby, fingerprinty
obou CSV schémat a případnou cestu k zachovaným raw artefaktům. Třídy se mapují
podle qualified name; metody a konstruktory podle třídy, jména, arity a typů
parametrů. Nejednoznačné mapování je diagnostika a příslušný řádek se
neimportuje. CK source-level chyba ukončí provider, aby částečné výsledky nebyly
označeny jako přesné.

Alternativně lze nástroj spustit bez shaded JARu. JDT potřebuje i tranzitivní
závislosti, samotné `target/classes` nestačí:

[source,bash]
----
mvn -q compile
CP="target/classes:$(mvn -q dependency:build-classpath -Dmdep.outputFile=/dev/stdout)"
java -cp "$CP" cz.utulnykoutek.metrics.cli.Main cesta/k/Soubor.java

# Příklad se závislostí na Java Core API (java.util, java.time):
java -cp "$CP" cz.utulnykoutek.metrics.cli.Main \
  src/test/resources/cz/utulnykoutek/metrics/sample/Nested.java --release 17
----

== Výstupní formáty

* `text` (výchozí) — stromový přehled přímo deklarovaných členů;
* `json` — T1 schema s baseline metadaty, typy, relacemi, dependency edges a
  coverage;
* `preview` — barevný ANSI/YAML strom.

[source,bash]
----
java -jar target/java-metrics-1.0-SNAPSHOT.jar cesta/k/Soubor.java --format text
java -jar target/java-metrics-1.0-SNAPSHOT.jar cesta/k/Soubor.java --format json
java -jar target/java-metrics-1.0-SNAPSHOT.jar cesta/k/Soubor.java --format preview
----

Příklad textového výstupu:

[source,text]
----
Package: cz.utulnykoutek.metrics.sample

Outer [class]
  Declared: methods=2, constructors=1, fields=3

  Inner [class]
    Declared: methods=3, constructors=1, fields=2

    DeepInner [class]
      Declared: methods=2, constructors=0, fields=0
----

== End-to-end demo built-in měření

Následující příklad provede celý základní tok nad testovacím souborem:
naparsování JDT, vytvoření `AnalysisContext`, výpočet metrik přes
`JavaMetricsProvider`, uložení výsledků do `MeasurementStore` a textový i
barevný preview výstup.

Nejkratší CLI varianta:

[source,bash]
----
mvn -q package
INPUT=src/test/resources/cz/utulnykoutek/metrics/sample/Nested.java

java -jar target/java-metrics-1.0-SNAPSHOT.jar "$INPUT" --format text
java -jar target/java-metrics-1.0-SNAPSHOT.jar "$INPUT" --format preview
----

CLI interně používá stejnou provider pipeline jako následující programové
demo. Jeho úplný a přímo spustitelný zdroj je v `BuiltInDemo.java` v kořeni
repozitáře:

[source,java]
----
import cz.utulnykoutek.metrics.analysis.BaselineMetadata;
import cz.utulnykoutek.metrics.domain.PackageCompound;
import cz.utulnykoutek.metrics.export.TextExporter;
import cz.utulnykoutek.metrics.export.YamlPreviewConverter;
import cz.utulnykoutek.metrics.metrics.AnalysisContext;
import cz.utulnykoutek.metrics.metrics.JavaMetricsProvider;
import cz.utulnykoutek.metrics.metrics.ProviderResult;
import cz.utulnykoutek.metrics.metrics.definition.BuiltInMetricDefinition;
import cz.utulnykoutek.metrics.metrics.measurement.NumericResult;
import cz.utulnykoutek.metrics.parser.JdtParser;

import java.nio.file.Path;
import java.util.List;

public final class BuiltInDemo {
    public static void main(String[] args) throws Exception {
        Path input = args.length == 0
                ? Path.of("src/test/resources/cz/utulnykoutek/metrics/sample/Nested.java")
                : Path.of(args[0]);

        // 1. Parsování zdroje a zachycení reprodukčních metadat.
        JdtParser.Config parserConfig = new JdtParser.Config();
        BaselineMetadata baseline = BaselineMetadata.capture(parserConfig);
        PackageCompound pkg =
                (PackageCompound) new JdtParser(parserConfig).parse(input);

        // 2. Projektový kontext předaný všem measurement providerům.
        AnalysisContext context = new AnalysisContext(
                List.of(pkg),
                List.of(input),
                baseline);

        // 3. Vlastní provider a jeho skutečně implementované built-in definice.
        JavaMetricsProvider provider = new JavaMetricsProvider();
        for (BuiltInMetricDefinition definition : provider.definitions()) {
            System.out.printf("definition: %s [%s], spec=%s%n",
                    definition.id(),
                    definition.unit(),
                    definition.specificationKey());
        }

        // 4. Výpočet. Provider nemutuje doménový strom; vrací samostatná měření.
        ProviderResult providerResult = provider.measure(context);
        providerResult.measurements().all().forEach(measurement -> {
            NumericResult result = (NumericResult) measurement.result();
            System.out.printf("%s  %s  value=%s  status=%s  run=%s%n",
                    measurement.metricId(),
                    measurement.subject().id(),
                    result.value(),
                    measurement.status(),
                    measurement.providerRunId());
        });

        // 5. Výpisy používají stejné hodnoty z MeasurementStore.
        System.out.println(TextExporter.render(pkg, providerResult));
        System.out.println(YamlPreviewConverter.render(pkg, providerResult));
    }
}
----

Skript `run-demo.sh` sestaví hlavní projekt, vytvoří classpath Maven závislostí,
zkompiluje kořenový `BuiltInDemo.java` do `target/demo-classes` a spustí jej:

[source,bash]
----
./run-demo.sh

# Volitelně lze předat jiný jeden Java zdrojový soubor:
./run-demo.sh cesta/k/Soubor.java
----

Výchozí `JavaMetricsProvider` registruje `MemberCountComputer`,
`SourceLineMetricsComputer` a `Lcom4Computer`:

* `java.declared-methods`;
* `java.declared-constructors`;
* `java.declared-fields`;
* `java.physical-loc` a `java.ncloc` pro project/file/package/type, explicitní
  členy, inicializační bloky a lambdy;
* `java.physical-loc-exclusive` a `java.ncloc-exclusive` pro typ bez nested types.
* `java.lcom4` pro class-like typy, včetně statusu úplnosti a auditních
  atributů grafu.
* `java.ca` a `java.ce` jako počty unikátních příchozích a odchozích interních
  package dependencies; external/JDK a unresolved podklad zůstává v auditních
  atributech.
* `java.instability` jako Martinův poměr `Ce / (Ca + Ce)`, s explicitním
  `NOT_APPLICABLE` pro skutečně izolovaný balík a částečným výsledkem při
  nerozřešených package targets.
* `java.abstractness` jako podíl top-level interfaces a explicitně abstract
  classes mezi top-level class/interface/record/enum typy vstupního manifestu.
* `java.distance` jako normalizovaná absolutní vzdálenost
  `|abstractness + instability - 1|` od Martinovy main sequence.

Jde pouze o členy přímo deklarované v daném typu. Zděděné členy, členy
vnořených typů a enum konstanty se nezapočítávají. Rekurzivní member counts se
nepočítají.

== Chyby a neúplné bindings

Syntaktické chyby se vypíšou na `stderr` ve formátu
`soubor:řádek:sloupec: zpráva` a program skončí s exit kódem `1`.
Binding resolution je ve výchozím stavu zapnutá (`setResolveBindings(true)`).
Chybějící závislosti (importy, rodičovské třídy, neznámé typy) analýzu
nezastaví, ale pro plnou přeložitelnost lze dodat `--classpath`, `--sourcepath`
a `--release`.

== Aktuální stav implementace

Implementováno podle `docs/01-research-plan.adoc`:

* *T0 baseline* — JSON schema, integrační Maven test, metadata JDT/JDK/parseru
  (`docs/04-t0-baseline.adoc`, `docs/10-baseline.adoc`);
* *T1 identity symbolů a bindings* — `SymbolRef`, relace
  `inheritance`/`implementations`/`overrides`, `dependencyEdges`,
  `BindingCoverage` a JSON export T1 schema.
* *T2 metrická infrastruktura* — strukturované a namespacované `MetricId`,
  verzované `MetricDefinition`, immutable `MetricCatalog`, `SubjectRef`,
  explicitní přesné/částečné/nedostupné/neaplikovatelné výsledky a validovaný
  immutable `MeasurementStore`; nový nemutující kontrakt `MeasurementProvider`,
  `JavaMetricsProvider` a `MemberCountComputer` pro přesná měření
  `java.declared-methods`, `java.declared-constructors` a
  `java.declared-fields`; `SourceSpan` a `SourceLineMetricsComputer` počítají
  `java.physical-loc`, `java.ncloc` a type-exclusive varianty přímo ze zdroje.
  Inicializační bloky a lambdy mají vlastní stabilní identity, source ranges
  a measurements; lambda navíc odkazuje na bezprostřední enclosing subject.
  Ruční oracle pokrývá 186 hodnot pro 25 typů, 39 explicitních členů,
  dva inicializátory a dvě lambdy v
  `basic-members`, `inheritance`, `interfaces`, `coupling`, `overloads`,
  `nested-types`, `modern-types`, `initializers-lambdas` a
  `unresolved-dependency`; první vrstva `java.lcom4` přidává immutable
  `TypeCohesionEvidence`/`MethodCohesionEvidence` pro eligible methods,
  instance-field accesses, intra-type calls a unresolved evidence;
  `CohesionEvidenceExtractor` tento model plní z JDT bindings, zahrnuje lambdy,
  izoluje těla nested typů a strukturálně rozpoznává triviální accessors;
  `Lcom4Computer` publikuje `java.lcom4`, rozvíjí volané accessors na backing
  fields a rozlišuje `EXACT`, horní mez `PARTIAL` a důvody
  `NOT_APPLICABLE`;
  `PackageDependencyGraphBuilder` agreguje type dependencies na immutable
  package graph, odstraňuje self-package hrany, deduplikuje dvojice balíků a
  odděluje internal, external, JDK a unresolved cíle; JDT body extrakce
  zahrnuje local types, instantiations/constructors, calls, field accesses,
  casts, `instanceof`, class literals, method references, catches, lambda
  targets a konkrétní generic arguments;
  `ProjectMetricAggregator` a `ProjectAggregationExporter` poskytují
  deterministickou project-level agregaci s oddělenou sensitivity vrstvou a
  JSON/CSV exportem;
  `MartinCouplingComputer` nad grafem publikuje interní `java.ca`/`java.ce` a
  odvozenou `java.instability`; unresolved package target mění počty na dolní
  meze a poměr na `OBSERVED_FRAGMENT`, případně interval `[0,1]`;
  `AbstractnessComputer` publikuje `java.abstractness`, vylučuje annotations a
  non-top-level typy a zachovává auditní čitatele/jmenovatele;
  `MartinCouplingComputer` z obou vstupů odvozuje `java.distance` a propaguje
  jejich `NOT_APPLICABLE`, `OBSERVED_FRAGMENT` nebo bezpečný interval;
  všech pět Martinových metrik má 55řádkový ruční package oracle a
  reprodukovatelný report v `docs/31-martin-validation-report.adoc`;
  `ProjectMetricAggregator` poskytuje první vrstvu project-level agregací:
  completeness counts a Type 7 deskriptivní statistiky pouze nad přesnými
  `OK` hodnotami, striktně oddělené podle metriky, scope a provider run;
* *konfigurace běhu* — striktní typované TOML schema 1, precedence
  defaults/TOML/CLI, validace, výpis effective konfigurace a SHA-256
  provenance;
* *CK provider* — izolovaný `CkProcessRunner`, zmrazené class/method CSV schema,
  `CkSubjectMapper`, `CkMetricsProvider`, obecný JSON export měření a provenance.
* *společný validační corpus* — devět malých Maven projektů v `validation/`,
  build/subject/measurement oracle a spustitelný `ValidationCorpusTest` pro
  built-in provider; opt-in `CkValidationCorpusTest` spouští skutečný připnutý
  CK JAR nad všemi případy, ověřuje mapování a automaticky použije doplněné
  `ck.*` oracle. Všech 17 definic podporujících type scope má type-level oracle:
  vedle počtů členů, DIT/NOC, WMC/RFC/LOC jsou dokončeny
  CBO/modified CBO, fan-in/fan-out a LCOM/LCOM*/TCC/LCC. Member-only
  `ck.parameters` a method/constructor scope metrik `ck.wmc`, `ck.rfc` a
  `ck.loc` jsou dokončeny, tedy
  pro 61 stabilních type/member subjects. Pro platné `ck.tcc` a `ck.lcc` je
  povinné `variables-and-fields=true`; hodnota `false` vypne jejich závislost
  na method-field usage a tiše vrací neplatné nuly. Samostatná reprodukce je v
  `docs/21-ck-tcc-lcc-anomaly.adoc`;
  stejné vstupy jsou připravené pro budoucí CKJM-extended;
* *Maven Site a Javadoc* — `mvn site` generuje API dokumentaci
  (maven-javadoc-plugin) a projektové reporty; v `.gitlab-ci.yml` se
  publikuje přes GitLab Pages (`deploy-pages` job).

Připraveno k implementaci:

* *T2 další výpočty OO metrik* — schválené definice v
  `docs/07-t2-metric-decisions.adoc` a specifikace v `docs/08-t3-metrics.adoc`;
  rozšíření importu CK o další zmrazené syntaktické sloupce a validace
  mapování na širším oracle, CKJM-extended 2.11 jako externího
  bytecode text/XML provideru a PMD 7.29.0 pro všech 13 metrik jeho
  `JavaMetrics` API;
* *Checkstyle* — threshold/violation provider pro šest Metrics Checks a předem
  zmrazený style/design ruleset, nikoli úplný export číselných hodnot;
* *DesigniteJava Community* — open-source externí CLI/CSV provider pro 17
  design smells, 10 implementation smells a 13 metrických variant;
* *vlastní metriky* — implementované physical LOC/NCLOC a LCOM4; dále zbývají
  zejména Martinovy package metriky, vybrané QMOOD/L&K varianty a
  coverage-aware agregace;
* *T3 validace* — základ společného corpusu a type-level oracle všech
  publikovaných `ck.*` metrik jsou implementovány; u CK zbývá zejména
  stabilizace identity local/anonymous typů, generics a formální report neshod;
  všechny scope publikovaných CK metrik již mají oracle. CKJM oracle přijde s
  jeho providerem;
* *T4 experiment runner* — plánován v `docs/01-research-plan.adoc`.

Externí hodnoty budou namespacované (`ck.*`, `ckjm.*`, `pmd.*`,
`checkstyle.*`, `designite.*`) a doplněné verzí a konfigurací. Externí knihovny nebudou
linkovány přímo do parserového procesu `java-metrics`.
